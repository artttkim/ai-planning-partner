# 화면 설계

먼저 `pw-standards` 스킬의 공통 기준을 따른다.

## 입력과 산출물

| 구분 | 내용 |
|---|---|
| 입력 | `과제요약.md`, 유저 플로우(있으면), `회사/화면지도/`(있으면), `회사/규칙.md`, 기획자가 준 캡처 |
| 원본 | `원본/NN_화면설계/<화면 ID>.md` 화면마다 파일 하나. 형식은 이 스킬 폴더의 `template.md` |
| 생성물 | 엔진 `build pptx`(화면 설계서), `build dev`(개발용 화면 명세) |
| 점검 | 이 스킬 폴더의 `checklist.md`, 엔진 `validate` |
| 다음 연결 | 기능 명세 / 정책 단계. 설명에 적은 정책 ID를 넘긴다 |

`NN`은 과제요약 진행 단계의 순서 번호다 (예: 화면 설계가 3번째면 `03_화면설계`).

## 작성 순서

### 1. 화면 목록

- 기능(`FR-`)마다 그 기능이 일어나는 화면을 찾는다. 유저 플로우가 있으면 그 화면을 쓴다.
- 기존 화면을 고치는 과제는 화면 지도나 캡처의 현재 화면을 바탕으로 바뀌는 부분만 고친다. 바뀐 요소에 `changed: true`.
- 구분: 신규(새 화면), 변경(기존 화면 수정), 참고(바뀌지 않지만 흐름 이해에 필요. 설명 표 생략 가능)
- 화면 ID는 2장 ID 체계를 따른다.

### 2. 화면 구성

`components`에 위에서 아래 순서로 구성 요소를 적는다. 위치(`x, y, w, h`, px 기준)를 적지 않으면 엔진이 위에서부터 차례로 쌓는다. 팝업처럼 위치가 중요한 요소만 위치를 적는다.

- 기준 크기: 앱 `frame: mobile` 360×800, 웹 `frame: web` 1440×1024
- 무채색, 낮은 충실도. 이미지는 `이미지`, 아이콘은 `아이콘` 요소로 대신한다.
- 문구는 실제로 쓸 문구를 쓴다. 정하지 못한 문구는 `TBD`.

**쓸 수 있는 구성 요소 (type)**

| 분류 | 요소 |
|---|---|
| 구조 | 상단바, 하단탭바, 탭, 구분선 |
| 입력 | 입력창, 검색창, 선택상자, 체크박스, 라디오, 토글 |
| 실행 | 기본버튼, 보조버튼, 텍스트링크, 플로팅버튼 |
| 표시 | 제목, 본문, 목록, 카드, 표, 이미지, 아이콘, 배지 |
| 피드백 | 오류문구, 안내문구, 팝업, 바텀시트, 토스트, 로딩, 빈화면 |

### 3. 화면별 설명

- 설명할 요소에 `marker: <번호>`를 달고, 설명 표에 같은 번호로 쓴다. 번호는 위에서 아래 순서로 1부터.
- 설명에는 해당하는 것을 쓴다: 동작(누르면 SCR-020으로 이동), 조건(모두 입력되면 활성화), 값(최대 20자), 문구, 정책 연결.
- 개발자와 AI가 질문 없이 만들 수 있는 수준으로 쓴다.
- 정책이 길거나 여러 화면에 걸치면 설명에는 요약과 정책 ID만 쓴다. 정책 ID는 이 단계에서 먼저 만들어 둔다.
- 변경 화면은 바뀐 요소만 설명한다.

### 4. 상태 화면

빈 화면, 오류, 로딩, 권한별 상태가 있는지 확인한다. 기본 화면과 일부만 다르면 설명에 적고, 구성이 크게 다르면 별도 화면 파일로 만든다.

### 5. 점검과 생성

1. `checklist.md`로 점검하고 고친다.
2. 엔진 `validate`로 ID 연결을 검사하고, 나온 문제를 고친다.
3. 엔진 `build all`로 화면 설계서와 개발용 명세를 만든다.

### 6. 검수함에 올리기

`pw-standards` 7장 형식으로 올린다. 요약에는 화면 목록(ID, 이름, 구분)과 생성한 파일 이름을 쓴다.

결정 필요로 올리는 것은 화면 구조나 흐름이 크게 달라지는 선택뿐이다 (예: 별도 화면 vs 바텀시트). 배치, 문구, 요소 선택은 올리지 않는다.
