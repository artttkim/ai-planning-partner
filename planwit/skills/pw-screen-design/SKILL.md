# 화면 설계

먼저 `pw-standards` 스킬의 공통 기준을 따른다.

## 입력과 산출물

| 구분 | 내용 |
|---|---|
| 입력 | `00_과제요약.md`, 유저 플로우(있으면), `<서비스>/디자인/화면지도/`(있으면), `회사/규칙.md`, 기획자가 준 캡처 |
| 원본 | `2_기획문서/NN_화면설계/<화면 ID>.md` 화면마다 파일 하나. 형식은 이 스킬 폴더의 `template.md` |
| 생성물 | 엔진 `build all`: `3_결과물/기획안.html`(프로토타입 + 설명 + 의견). 화면 설계서(.pptx)는 기획자가 요청할 때만 `build pptx` |
| 점검 | 이 스킬 폴더의 `checklist.md`, 엔진 `validate` |
| 다음 연결 | 기능 명세 / 정책 단계. 설명에 적은 정책 ID를 넘긴다 |

`NN`은 과제요약 진행 단계의 순서 번호다 (예: 화면 설계가 3번째면 `03_화면설계`).

## 작성 순서

### 0. 기존 화면 방식 먼저

새로 그리거나 고치는 화면마다, 그리기 전에 서비스에 이미 있는 **가장 비슷한 화면**을 찾아 그 방식을 따른다. 새 방식을 만들지 않는다.

- 찾는 곳: `<서비스>/디자인/화면지도/`(캡처, 기존화면 패턴 메모), `<서비스>/기준본/화면/`, 기획자가 준 캡처, 기획자가 준 피그마(읽기만).
- 따를 것: **위치**(어느 메뉴 아래에 두는지. 예: 설정 항목은 기존 설정 화면 묶음 안), **구성**(목록, 줄, 토글, 팝업 모양), **문구**(안내, 빈 결과, 오류 문구의 말투와 형식), **흐름**(고르면 바로 저장인지, 완료 버튼인지).
- 예: 나라 고르기 → 기존 언어 설정 목록과 "시스템 설정" 항목, 검색 결과 없음 → 기존 지역 검색의 문구, 알람 설정 항목 → 진동처럼 "이름 + 토글" 한 줄.
- 화면 파일 맨 위 정보에 `- 참고 화면: <따른 기존 화면>`을 쓴다. 기획안에 그대로 보인다.
- 비슷한 기존 화면을 찾을 자료가 없으면 지어내지 않는다. 가장 단순한 형태로 그리고 검수함 "확인만"에 "기존 화면 확인 필요: <화면>"을 남기며, 기획자에게 해당 기존 화면 캡처를 `<서비스>/디자인/화면지도/`에 넣어 달라고 한 줄로 부탁한다.
- 찾은 기존 화면의 방식은 `<서비스>/디자인/화면지도/기존화면_패턴.md`에 한 줄씩 모아 둔다. 다음 과제에서 다시 찾지 않게 하기 위해서다.

### 1. 화면 목록

첫 검수 때 만든 뼈대 화면이 있으면 그것을 이어서 채운다. 뼈대의 `- 뼈대:` 비고는 다 채운 뒤 지운다.

**과제요약의 기능(`FR-`)을 하려면 꼭 있어야 하는 화면만 그린다.** 다른 설계서에 흔히 있는 화면이라고 넣지 않는다.

- 기능(`FR-`)마다 그 기능이 일어나는 화면을 찾는다. 유저 플로우가 있으면 그 화면을 쓴다.
- 과제요약에 없는 기능의 화면은 만들지 않는다. 예: 요청에 없는 신고, 업데이트 안내, 바뀐 점 안내, 온보딩, 튜토리얼. 필요해 보이면 화면을 그리지 않고 검수함 "확인만"에 "추가 제안"으로 한 줄씩 남긴다.
- 기존 화면을 고치는 과제는 화면 지도나 캡처의 현재 화면을 바탕으로 바뀌는 부분만 고친다. 바뀐 요소에 `changed: true`.
- 구분: 신규(새 화면), 변경(기존 화면 수정), 참고(바뀌지 않지만 흐름 이해에 필요. 설명 표 생략 가능)
- 화면 번호는 `pw-standards` 2장을 따른다. 새 화면은 엔진 `next-id`로 번호를 받는다. 서비스 기준본(`<서비스>/기준본/화면/`)에 이미 있는 화면을 고치면 `base`로 가져와 고치고, 기준본에 없는 기존 화면은 "변경"으로 새로 그린다.
- 다른 과제가 같은 화면을 고치고 있으면(`validate`의 "확인할 것") 그 과제의 화면을 참고해 어긋나지 않게 그리고, 검수함 "확인만"에 남긴다.

### 2. 화면 구성

구성은 **화면에 무엇이 어디에 놓이는지**를 적는 것이다. 요소를 설명하는 글을 상자에 적는 것이 아니다. 엔진이 이 구성으로 실제 앱 모양의 디자인 화면을 그리고, 그 캡처 위에 번호를 찍어 화면 설계서를 만든다. 디자이너와 개발자가 그림만 보고 화면을 옮길 수 있어야 한다.

**원칙**
- 화면에 실제로 보이는 요소 하나를 구성 요소 하나로 그린다. 버튼 3개를 "복사 | 공유 | 재발급" 같은 글자 하나로 쓰지 않는다.
- 나란히 놓이는 요소는 `행`으로 묶는다. 위아래로 놓이는 묶음은 `카드`(테두리 있음)나 `묶음`(테두리 없음)으로 묶고 `children`에 넣는다.
- 목록은 실제처럼 보이는 예시 데이터로 2~3줄만 그린다. 줄마다 같은 구조(`행`: 아바타, 본문, 버튼)로 쓴다.
- `label`에는 화면에 보이는 글자만 쓴다. 조건, 동작, 권한 설명("방장에게만 보임")은 설명 표에 쓴다.
- 한 장에는 한 상태만 그린다. 다른 상태는 4장을 따른다.
- 이미 있는 화면을 고치면 캡처의 배치를 그대로 따르고, 바뀐 요소에만 `changed: true`.
- 색, 글꼴, 모서리 같은 디자인 값은 구성에 적지 않는다. 엔진의 기본 디자인 값을 쓰고, 서비스의 `<서비스>/디자인/디자인.css`가 있으면 그 값을 따른다. 사진이나 그림은 `이미지`, 아이콘은 `아이콘`(이름)으로 쓴다.
- 문구는 실제로 쓸 문구를 쓴다. 정하지 못한 문구는 `TBD`.

**배치.** 위치(`x, y, w, h`)는 적지 않는다. 엔진이 360×800(앱) 또는 1440×1024(웹) 실제 축척으로 쌓는다. 상단바, 탭, 하단탭바는 화면 너비 전체를 쓰고, 나머지는 좌우 16px 여백 안에 놓인다. 팝업, 바텀시트, 토스트, 플로팅버튼은 엔진이 제자리(가운데, 아래, 오른쪽 아래)에 놓는다. 팝업 화면(`-P1`)은 부모 화면을 어둡게 깔고 그 위에 그린다. 내용이 800px보다 길면 화면이 아래로 길어진다.

**쓸 수 있는 구성 요소 (type)**

| 분류 | 요소 | 쓰는 속성 |
|---|---|---|
| 구조 | 상단바 | `label`(제목), `left`/`right`(아이콘 이름: 뒤로, 닫기, 더보기, 검색 등), `align` |
| 구조 | 탭, 하단탭바 | `items`(항목 이름), `selected`(선택 순서, 0부터) |
| 구조 | 행 | `children`을 가로로 놓는다. 아이콘, 아바타, 배지, 텍스트링크, 토글, `size: small` 버튼은 제 크기만, 나머지는 남은 너비를 나눈다. `w`로 너비를 정할 수 있다 |
| 구조 | 카드, 묶음, 목록 | `children`을 세로로 놓는다. 목록은 줄 사이에 구분선을 넣는다 |
| 구조 | 구분선 | |
| 입력 | 입력창, 검색창, 선택상자 | `label`(안내 문구나 입력된 값) |
| 입력 | 라디오, 체크박스 | `items`, `selected`. 하나만 있으면 `label`, 켬은 `selected: 1` |
| 입력 | 토글 | `label`(왼쪽 글자), `selected: 1`이면 켬 |
| 실행 | 기본버튼, 보조버튼 | `label`, `size: small` |
| 실행 | 텍스트링크, 플로팅버튼 | `label` |
| 표시 | 제목, 본문, 안내문구, 오류문구 | `label`, `align`(center, right) |
| 표시 | 아이콘, 아바타, 배지, 이미지, 표 | `label` |
| 피드백 | 팝업, 바텀시트 | `label`(첫 줄 제목, 다음 줄부터 본문), `children`(버튼 등) |
| 피드백 | 토스트, 로딩, 빈화면 | `label`. 빈화면은 `children`도 쓸 수 있다 |

모든 요소에 `id`(화면 안에서 고유), `marker`, `changed`를 쓸 수 있다. `children` 안 요소에도 번호를 달 수 있다.

### 3. 화면별 설명 (스크립트)

설명할 요소에 `marker: <번호>`를 달고, 설명 표에 같은 번호로 쓴다. 번호는 위에서 아래 순서로 1부터. **항목** 칸은 화면에 보이는 요소 이름을 쓴다.

**기준은 하나다: 개발자나 이해관계자가 이 설명만 보고 이해할 수 있고, 꼭 필요한 내용이 빠지지 않았는가.**

꼭 들어가야 하는 것 (해당하는 것만)
- 언제 보이는지, 처음 상태 (조건에 따라 보이거나 숨는 요소)
- 누르거나 입력하면 무슨 일이 일어나는지, 어느 화면으로 가는지
- 제한과 저장 시점 (필수, 글자 수, 바로 저장인지 "저장"을 눌러야 하는지)
- 실패하거나 쓸 수 없을 때 어떻게 되는지

쓰는 법
- 자연스러운 짧은 문장으로, 한 줄에 한 가지, 일어나는 순서대로 쓴다. 줄은 `<br>`로 나눈다. "노출:", "동작:" 같은 머리말은 붙이지 않는다.
- 다른 화면은 이름과 번호를 함께 쓴다. 예: 기준 국가 확인 팝업(SCR-100-P1)
- 화면 문구는 큰따옴표로 실제 문구를 쓴다. 숫자는 단위와 함께 쓴다.

빼는 것
- 그림만 봐도 알 수 있는 모양과 배치 (어떤 기존 화면을 따랐는지는 `참고 화면`에 쓴다)
- 왜 그렇게 정했는지 (결정 기록에 쓴다)
- 여러 화면에 같은 처리 (공통 정책 ID만 정책 칸에)

- 개발자와 AI가 질문 없이 만들 수 있는 수준으로 쓴다.
- 정책이 길거나 여러 화면에 걸치면 설명에는 요약과 정책 ID만 쓴다. 정책 ID는 이 단계에서 먼저 만들어 둔다.
- 변경 화면은 바뀐 요소만 설명한다.
- 실패 처리는 그 요소에만 해당하는 것(예: 상한에 닿았을 때 문구)만 설명에 쓴다. 로딩, 불러오기 실패, 서버 오류처럼 여러 화면에 같은 처리는 4장의 공통 상태 정책 ID만 정책 칸에 쓴다.

**비고.** 장표 아래 비고는 짧게 두 줄 이내로, 그 화면에만 해당하고 번호를 달 수 없는 참고만 쓴다 (예: "시간 선택 방식은 기존과 같다"). 아래는 비고에 쓰지 않는다.

| 내용 | 쓸 곳 |
|---|---|
| 모양이 다른 상태 (빈 화면, 수정 모드, 권한별 화면) | 별도 화면 (4장) |
| 로딩, 실패, 서버 오류, 권한을 잃은 뒤 처리 | 공통 상태 정책 (4장) |
| 상태별 버튼, 문구 표 같은 규칙 | 기능 명세 / 정책 |
| 요소 하나의 동작, 조건, 문구 | 그 요소의 설명 |

### 4. 상태 화면

빈 화면, 오류, 로딩, 권한별 상태가 있는지 확인하고 아래처럼 나눈다.

- **모양이 다른 상태**(빈 화면, 수정 모드, 권한별로 요소가 크게 다름): 별도 화면 파일로 그린다. ID는 기본 화면 다음 번호를 쓴다 (예: SCR-020의 빈 화면은 SCR-025). 기본 화면 설명에는 "~이면 SCR-025를 보여 준다" 한 줄만 쓴다.
- **요소 하나만 다른 상태**(버튼 비활성, 배지 추가): 그 요소의 설명에 쓴다.
- **여러 화면에 같은 상태**(불러오는 중, 불러오기 실패, 서버 오류, 없어진 대상, 권한을 잃은 뒤): 과제에 공통 상태 정책 하나(`POL-`)를 만들어 한 번만 쓰고, 해당 화면의 설명 정책 칸에 그 ID를 단다. 화면마다 반복하지 않는다.

### 5. 점검과 생성

1. `checklist.md`로 점검하고 고친다.
2. 엔진 `validate`로 ID 연결을 검사하고, 나온 문제를 고친다.
3. 엔진 `build proto`로 화면 캡처(`.planwit/프로토타입/*.png`)를 만들어 직접 보고, 글자가 잘리거나 겹친 곳이 있으면 구성을 고친다.
4. 엔진 `build all`로 기획안과 개발 명세를 만든다.
   - 화면 설계서(.pptx)는 기획자가 요청할 때만 `build pptx "<과제>"`로 만든다. 화면 그림은 기본이 디자인 화면이고, 와이어프레임을 원하면 `--look wire`(과제에 저장되어 다음에도 그대로 쓴다).
   - 디자인 화면은 초안이다. 검수함 요약에 "디자인 시안이 아니라 기획 확인용 화면"이라고 적는다.

### 6. 검수함에 올리기

`pw-standards` 7장 형식으로 올린다. 요약에는 화면 목록(ID, 이름, 구분)과 생성한 파일 이름을 쓴다.

결정 필요로 올리는 것은 화면 구조나 흐름이 크게 달라지는 선택뿐이다 (예: 별도 화면 vs 바텀시트). 배치, 문구, 요소 선택은 올리지 않는다.
