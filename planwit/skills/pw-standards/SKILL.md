# 플랜윗 공통 기준

모든 단계 스킬은 이 기준을 따른다. 단계 스킬에는 이 기준과 다른 점만 적는다.

## 1. 기준 적용 순서

같은 항목에 기준이 여럿이면 위의 것을 따른다.

1. 과제 지시: 과제의 PRD, 기획자의 대화 요청
2. 회사 규칙: 작업 공간의 `회사/규칙.md`
3. 기본 기준: 이 문서

업계 기준(5장)은 순서와 별개로 항상 점검에 쓴다. 회사 규칙이 업계 기준과 어긋나면 회사 규칙을 따르고 검수함 "확인만"에 남긴다.

## 2. ID 체계

| 종류 | 형식 | 연결 |
|---|---|---|
| 기능 | `FR-001` (하위 기능 `FR-001-1`) | |
| 화면 | `SCR-010` (10 단위, 사이에 끼우면 `SCR-015`) | FR 참조 |
| 화면 위 요소 (팝업, 바텀시트) | `SCR-010-P1` | 부모 화면 |
| 정책 | `POL-001` | FR 참조 |
| 수용 기준 | `AC-001-1` | FR, POL 참조 |
| 개발 태스크 | `TASK-001` | AC 참조 |

화면(`SCR`)과 정책(`POL`) 번호는 **서비스 전체에서 하나뿐**이다. 여러 과제를 나눠 작업한 뒤 서비스 기준본에 합치기 위해서다.

- 새 화면이나 새 정책 번호는 엔진 `next-id "<과제>"`(정책은 `--policy`)로 받는다. 과제 안에서 임의로 붙이지 않는다. 팝업은 부모 번호에 `-P1`.
- 서비스 기준본(`서비스/화면/`, `서비스/정책.md`)에 이미 있는 화면이나 정책을 고칠 때는 엔진 `base "<과제>" <번호>`로 가져와서 고친다. 가져온 파일에 기준본 지문이 적혀 합칠 때 충돌을 검사한다.
- 기능(`FR`), 수용 기준(`AC`), 개발 태스크(`TASK`)는 과제 안에서 붙인다.
- 엔진 `validate`가 다른 과제나 기준본과 번호가 겹치면 알려 준다. 같은 화면을 다른 과제도 고치고 있으면 "확인할 것"으로 알려 준다.
- 회사 규칙에 ID 규칙이 있으면 그것을 따른다.

## 3. 작성 기준

| 항목 | 기준 |
|---|---|
| 버전 | 초안 `v0.1`부터. 구성원 합의 후 `v1.0`, 이후 수정 `v1.1` |
| 문장 | 설명은 "~한다"체, 짧은 문장, 한 항목에 한 가지 |
| 화면 문구 | 해요체. 버튼은 동사형("저장하기"). 오류 문구는 원인과 해결 방법을 함께 |
| 숫자, 날짜 | 숫자는 단위와 함께(5회, 30분). 날짜는 `YYYY.MM.DD` |
| 모호한 표현 | "적절히", "빠르게", "등"을 쓰지 않고 값이나 목록으로 쓴다 |
| 모르는 값 | 지어내지 않고 `TBD`와 확인할 사람을 쓴다 |
| 근거 | 항목마다 근거를 남긴다: PRD 위치(예: PRD 2쪽), 회사 규칙, 업계 기준, 결정 기록 |

## 4. 산출물 기본 양식

회사 양식이 없으면 아래 양식으로 만든다.

| 산출물 | 형식 | 쓰임 |
|---|---|---|
| 기획안 | `기획안.html` 파일 하나 (기본) | 실제 앱 모양의 모든 화면을 눌러 이동하며 본다. 옆에 화면 목록, 번호별 설명, 개발 보기(요소 ID, 종류, 동작, 정책, 이동, YAML 복사). 기획자와 개발자가 같이 본다. 초안이며 디자인 시안이 아니다 |
| 개발 명세 | `개발명세.md` 파일 하나 (기본) | 개발자와 AI 코딩 도구용. 화면별 구성 YAML과 정책, 수용 기준, 개발 태스크를 ID로 이어 한 파일에 담는다 |
| 화면 설계서 | `.pptx` 16:9 (요청할 때만) | 표지, 변경 이력, 화면 목록, 화면별 장표(왼쪽 디자인 화면 캡처와 번호, 오른쪽 번호별 설명). 회사 양식 제출이 필요할 때 |
| 정책서 | `.docx` | 정책 ID, 대상, 조건과 값, 예외, 근거, 합의 상태 |
| 기능 목록 | `.xlsx` | FR, SCR, POL, AC의 연결 |

## 5. 업계 기준 (점검용)

과제 성격에 따라 강도를 조절한다. 신규 서비스(D 유형)는 보안, 개인정보, 비기능 요구사항을 핵심 리스크만 본다.

| 분야 | 기준 | 주로 보는 것 |
|---|---|---|
| 사용성 | 닐슨 사용성 휴리스틱 | 상태 표시, 오류 예방, 일관성 |
| 접근성 | KWCAG 2.2, WCAG 2.2 | 대체 텍스트, 명도 대비, 오류 안내 위치 |
| 플랫폼 | Apple HIG, Material Design | 내비게이션, 터치 영역(44pt, 48dp) |
| 요구사항 품질 | ISO/IEC/IEEE 29148 | 명확함, 검증 가능, 모순 없음 |
| 개인정보 | 개인정보 보호법 | 수집 최소화, 동의, 보관 기간 |

## 6. 모듈 공통 동작

| 항목 | 동작 |
|---|---|
| 진행 | 기획자에게 묻지 않고 끝까지 작성한다. 판단이 필요한 것은 추천안을 가정으로 적용한다 |
| 점검 | 단계의 체크리스트로 스스로 점검하고, 고칠 수 있는 것은 바로 고친다. 고친 내역은 보고하지 않는다 |
| 검수 | 요약, 결정 필요, 확인만 세 부분으로 검수함에 올린다 |
| 결정 필요 기준 | 되돌리기 어려운 결정, PRD나 기존 정책과 충돌, 근거로 추론할 수 없는 사업 판단, 다른 부서 합의가 필요한 것. 그 외는 "확인만" 또는 자동 처리 |
| 합의된 PRD | 내용을 바꾸지 않는다. 어긋나면 알리기만 한다 |
| 범위 | 과제요약의 기능(FR) 밖의 기능을 정책, 화면, 태스크로 만들지 않는다. 다른 서비스나 설계서에 흔히 있다는 이유로 넣지 않는다. 필요해 보이면 검수함 "확인만"에 "추가 제안"으로 한 줄만 남긴다 |

## 7. 검수함 항목 형식

```markdown
## <단계 이름> · 검수 대기

### 요약
- 핵심 내용 2~4줄

### 결정 필요
1. 질문
   - A. 선택지: 장단점
   - B. 선택지: 장단점
   - 추천: A. 이유 (현재 적용 중)

### 확인만
- 회사 규칙이나 업계 기준으로 정한 것 중 볼 가치가 있는 것
```

결정 필요나 확인만이 없으면 그 제목을 뺀다.

## 8. 과제 폴더 구조

과제 폴더는 아래 구조로만 만든다. 이름은 엔진(`engine/planwit/paths.py`)과 같아야 한다. 이 밖의 파일이나 폴더를 과제 폴더 맨 위에 만들지 않는다.

```
<작업 공간>/
├─ 회사/              규칙.md, 디자인.css(있으면), 화면지도/(기존 화면 캡처)
├─ 서비스/            서비스 기준본. 끝난 과제를 합친 전체 화면과 정책 (엔진 merge가 만든다)
│  ├─ 화면/  정책.md  화면목록.md  기획안.html  개발명세.md
└─ 과제/<YYYY-MM-DD>_<과제명>/
   ├─ 00_과제요약.md  요약, 진행 단계, 가정, 결정 기록, 변경 이력, 받은 요청 원문
   ├─ 01_검수함.md
   ├─ 1_입력자료/     받은 파일과 이미지_설명.md (파일을 받았을 때만. 붙여 넣은 글은 과제요약의 "받은 요청 원문")
   ├─ 2_기획문서/     단계별 원본. 번호는 과제요약 진행 단계 순서 (02_영향분석.md, 04_화면설계/ ...)
   ├─ 3_결과물/       엔진이 만든 기획안.html, 개발명세.md (화면 설계서 .pptx는 요청할 때만)
   └─ .planwit/       생성 기록, 캡처, 뽑은 텍스트 (기획자에게 보여 주지 않음)
```

결정 기록은 따로 파일을 두지 않고 `00_과제요약.md`의 "결정 기록" 장에 쓴다 (날짜, 결정, 이유, 출처).

예전 구조(`과제요약.md`, `원본/`, `회사양식/` 등)의 과제를 만나면 엔진 `migrate "<작업 공간>"`으로 옮긴 뒤 작업한다.

## 9. 작업 공간 경계

플랜윗은 플랜윗 전용 작업 공간 안에서만 일한다. 다른 작업 영역을 읽거나 고치지 않는다.

- 작업 공간: 맨 위에 `.planwit-workspace` 표시 파일이 있는 폴더. 예전에 만든 작업 공간은 `과제/`, `회사/`, 플랜윗 `CLAUDE.md`가 있는 폴더다.
- 지금 폴더가 작업 공간이 아니면 플랜윗 스킬은 파일을 만들거나 고치지 않는다. 기획자가 `setup`을 직접 요청한 경우만 예외다.
- 파일 쓰기는 작업 공간 안에서만 한다. 임시 파일도 과제의 `.planwit/`에 둔다.
- 작업 공간 밖의 자료(기획자가 준 파일 경로, 피그마 등 외부 도구)는 읽기만 한다. 필요한 파일은 과제의 `1_입력자료/`에 복사해 쓴다.
- 외부 도구에서 쓰기 기능(피그마 편집, 문서 생성, 메시지 보내기 등)은 기획자가 그 도구와 대상을 지정해 요청할 때만 쓴다.
