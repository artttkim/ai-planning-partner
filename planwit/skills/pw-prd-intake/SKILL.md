# PRD 접수

먼저 `pw-standards` 스킬의 공통 기준을 따른다.

## 입력과 산출물

| 구분 | 내용 |
|---|---|
| 입력 | `00_과제요약.md`의 "받은 요청 원문", `1_입력자료/`의 파일 (있으면, 텍스트로 바꾼 것 포함), 작업 공간의 `회사/규칙.md`, 서비스의 `<서비스>/디자인/화면지도/` (있으면) |
| 산출물 | 과제 폴더의 `00_과제요약.md` (이 스킬 폴더의 `template.md` 형식), 기획자에게 보여 줄 1페이지 요약과 질문 |
| 검수 | 1페이지 요약 확인. 플랜윗에서 유일하게 승인을 기다리는 검수 |
| 다음 연결 | 승인되면 진행 단계의 첫 단계 |

## 작성 순서

### 1. 구조화

PRD 내용은 바꾸지 않고 아래 항목에 나눠 담는다. 항목마다 상태(명시, 가정, 빈 곳)와 근거를 붙인다.

| 항목 | 비어 있으면 |
|---|---|
| 배경과 문제 | 가정으로 채움 |
| 목표 | 빈 곳 후보 |
| 타겟 사용자 | 기존 서비스 사용자로 가정 |
| 핵심 기능 | 빈 곳 후보. 기능마다 `FR-` ID와 우선순위 |
| 범위와 비범위 | 핵심 기능 외는 비범위로 가정 |
| 제약 | 비워 둠 |
| 성공 지표 | 비워 둠 (상세 기획을 막지 않음) |
| 관련자 | 비워 둠 |

- 명시: PRD에 있음. 근거에 원문 위치(예: `PRD.docx 2쪽`, `요청 원문 3번째 문단`)
- 가정: 회사 규칙, 화면 지도, 업계 통상 기준으로 추정. 근거에 추정 이유
- 빈 곳: 추정할 수 없음
- 핵심 기능 하나가 너무 크면 PRD 표현을 유지한 채 `FR-001-1`처럼 나눈다.
- PRD가 회사 정책이나 업계 기준과 어긋나면 바꾸지 않고 "확인할 것"에 적는다.

### 2. 과제 유형 판별

확신이 낮아도 묻지 않는다. 판별 결과와 이유를 요약에 보여 준다.

| 유형 | 주요 신호 |
|---|---|
| A. 기존 기능 수정 | "개선, 변경, 수정". 기존 화면 하나 또는 흐름 하나 |
| B. 여러 기능 개선 | 공통 목표로 기존 기능 여러 개를 바꿈 |
| C. 신규 기능 추가 | 기존 서비스에 없던 기능. 기존 화면과 이어지는 진입점이 있음 |
| D. 신규 서비스 | 새 서비스. 회원, 메인 같은 기본 구조부터 필요 |

섞이면 범위가 가장 큰 유형을 주 유형으로 한다 (A와 C가 섞이면 C).

### 3. 진행 단계 정하기

| 단계 | A | B | C | D |
|---|---|---|---|---|
| 방향 정의 | 생략 | 짧게 | 진행 | 진행 |
| 영향 분석 | 진행 | 진행 | 연결 지점만 | 생략 |
| 유저 플로우 / IA | 바뀌는 흐름만 | 진행 | 진행 | 진행 |
| 화면 설계 | 바뀌는 화면만 | 바뀌는 화면만 | 진행 | 진행 |
| 기능 명세 / 정책 | 진행 | 진행 | 진행 | 진행 |

- 수용 기준과 개발 태스크는 진행 단계에 넣지 않는다. 기획이 계속 바뀌는 동안에는 만들지 않고, 기획자가 개발에 전달할 때 `handoff` 스킬이 만든다.
- 진행할 단계는 모두 "대기"로 둔다. 모든 단계를 플랜윗이 작성한다. "준비 중"이라고 표시하거나 기획자에게 그렇게 말하지 않는다.
- 기획자가 이미 준 산출물의 단계는 빼고 그 산출물을 그대로 쓴다.
- 회사 규칙에 업무 프로세스가 있으면 그것을 따른다.

### 4. 빈 곳 질문

상세 기획을 막는 빈 곳만, 최대 3개 묻는다. 아래 중 하나에 해당해야 막는 빈 곳이다.

- 답에 따라 화면 구성이나 흐름이 크게 달라짐
- 답에 따라 범위가 크게 달라짐 (앱만인지 웹도인지 등)
- 되돌리기 어려운 핵심 정책
- PRD 안에서 서로 모순됨

그 밖의 빈 곳(버튼 문구, 세부 값, 성공 지표 등)은 묻지 않는다. 추천안을 가정으로 적용하거나 `TBD`로 둔다. 막는 빈 곳이 3개보다 많으면 영향이 큰 3개만 묻고, 나머지는 추천안을 가정으로 적용해 `01_검수함.md`의 결정 필요에 올린다.

질문마다 선택지 2~3개와 추천안, 추천 이유를 쓴다.

### 5. 방향 정의 (새 기능, 새 서비스)

진행 단계에 방향 정의가 있으면, 화면 뼈대보다 먼저 `2_기획문서/02_방향정의.md`를 쓴다 (`run` 스킬 "기본 작성"의 방향 정의 형식). 화면을 그리기 전에 무슨 경험을 만들고 왜 다시 오게 되는지를 정하기 위해서다. 화면 뼈대는 이 문서를 따라 그린다. 기획안 왼쪽 맨 위 "방향 정의"에서 함께 보인다.

### 6. 흐름 미리보기 (화면 뼈대)

화면 설계 단계가 있으면, 첫 검수 때 기획자가 방향을 한눈에 확인할 수 있게 화면 뼈대를 만든다. 글보다 화면 흐름을 볼 때 어긋난 곳을 훨씬 빨리 찾기 때문이다. 뼈대는 버리지 않고 화면 설계 단계에서 이어서 쓴다.

- 위치: `2_기획문서/NN_화면설계/` (NN은 진행 단계 표에서 화면 설계의 순서). 화면 번호는 엔진 `next-id`로 받고, 서비스 기준본에 있는 화면은 `base`로 가져온다 (`pw-standards` 2장).
- 화면마다 `pw-screen-design` 템플릿 형식으로 쓰되 가볍게: 상단바와 그 화면의 핵심 요소 2~4개만, 실제 문구로. 다른 화면으로 가는 요소에만 번호를 달고 설명은 "누르면 <화면 이름>(SCR-xxx)으로 간다." 한 줄만 쓴다 (기획안에서 눌러 이어 보기 위해). `## 비고`에 `- 뼈대: <이 화면의 역할 한 줄>`을 쓴다. 기존 화면 방식은 `pw-screen-design` 0장대로 먼저 찾고 `참고 화면`을 적는다. 기존 화면의 캡처가 있으면 뼈대도 `pw-screen-design` 2장 "캡처 화면"으로 쓴다 (다른 화면으로 가는 요소에만 위치와 번호).
- 기능(FR)마다 필요한 화면만 넣는다. 화면을 누르면 다음 화면으로 가도록 흐름 순서대로 요소를 둔다.
- 엔진 `build all "<과제>"`로 기획안을 만들고, `feedback` 스킬의 "기획안 열기"로 연다.

### 7. 1페이지 요약

한 화면에 들어가는 분량으로 아래만 보여 준다. 구조화 전체를 보여 주지 않는다.

```markdown
## <과제명> · 과제 요약

**유형**: <유형> (<판별 이유 한 줄>)
**목표**: <목표> (<근거>)
**핵심 기능**
- FR-001 <기능> (<근거>)
**진행할 단계**: <단계> → <단계> → ...
**한 문장**: <방향 정의의 한 문장>
**흐름 미리보기**: 기획안을 열어 뒀어요 (왼쪽 맨 위 "방향 정의"에 차별점, 습관 고리, 상황, 제약, 지표) (<주소>). 화면 <N>개: <화면 이름> → <화면 이름> → ... 이상한 곳은 기획안에 바로 적거나 여기에 말해 주세요.
**제가 이렇게 이해했어요** (틀린 줄만 고쳐 주세요)
- <가정을 기획자의 말로 한 줄씩, 3~5줄>
**질문**
1. <질문>
   - A. <선택지> / B. <선택지>
   - 추천: <선택지>. <이유>
**확인할 것**
- <PRD와 기존 정책이 어긋나는 점 등>
```

빈 부분(질문, 확인할 것 등)은 제목째 뺀다.

## 점검

- 모든 핵심 기능에 FR ID와 근거가 있다.
- PRD에 없는 내용을 "명시"로 표시하지 않았다.
- 질문은 3개 이하이고, 모두 막는 빈 곳 기준에 해당한다.
- 질문마다 추천안이 있다.
- 화면 설계 단계가 있으면 흐름 미리보기 뼈대가 있고, 기능(FR)마다 화면이 하나 이상 있다.
